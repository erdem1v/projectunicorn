Runtime-verifying Project Unicorn (Godot 4.6) through the Godot MCP:

**Logic / console checks:** `mcp__godot__editor-run` launches the project **headless** (`--headless -d`) — fine for driving systems + reading `mcp__godot__editor-debug-output` (the `[SalesSystem]/[EventManager]/[VH]` prints), but it has **no rendered viewport, so `capture-screenshot` returns nothing useful**. A throwaway harness scene that drives systems in `_ready()` and prints PASS/FAIL is the reliable pattern; do NOT call `get_tree().quit()` or the process dies before you can read output — leave it alive and `editor-stop` after.

**Screenshots / visual checks:** you must launch a **windowed** instance yourself, NOT via editor-run. Use PowerShell `Start-Process` with the args as a SINGLE quoted string (the project path contains a space — `…\project steam\…` — so a PowerShell array splits it and Godot aborts with "Invalid project path"):
`Start-Process godot.exe -ArgumentList '--path "C:\Users\erdem\Desktop\project steam\project-unicorn" res://scenes/test/<harness>.tscn'`
The runtime addon then prints "Server listening on port 7777" and `capture-screenshot` / `call-runtime-method` / `inspect-runtime-tree` target it.

**Port 7777 is single-instance:** only one game process binds the runtime addon. If another instance (a leftover playtest, or editor-run's headless one) holds it, the MCP runtime tools talk to the WRONG process (you'll see a different scene tree / stale save). Kill strays (`Get-CimInstance Win32_Process -Filter "name like '%godot%'"` → `Stop-Process`) before launching your windowed harness. The runtime tools (groups `runtime` + `testing`) are deferred — load via `tool-catalog`/ToolSearch.

**Reaching game state without onboarding:** a harness scene can `GameState.initialize_run(payload)` then mount `res://scenes/main/GameShell.tscn` and call `ProductSystem.start_build("ai_assistant", ["ai_assistant_chat","ai_assistant_memory"], "")`. Expose `vh_*` methods on the harness root and trigger them via `call-runtime-method` between screenshots. Note `initialize_run` does NOT reset `flags` or `CustomerRegistry`; `product_tab` re-routes only on `day_advanced`/sales signals (not `build_phase_changed`). `--skip-onboarding` / F12 also jump to GameShell (debug builds).

**Runtime bridge input/arg limitations (2026-07-13, verified the hard way):** `call-runtime-method` args CANNOT satisfy typed GDScript params — int/bool/Dictionary all fail (Dictionary throws an explicit "Cannot convert argument 1 from String to Dictionary" at the `callv` boundary; method not run). Only ARGLESS methods are reliable; for parameterized debug paths add an argless relay on a Node (statics unreachable — nodePath required), e.g. `GameShell.debug_force_month_extreme()`. **EXCEPTION — single String args DO marshal:** `call-runtime-method /root/EventBus emit_signal "<signal_name>"` works (returns 0) and fires the signal, so the reliable way to verify a debug HOTKEY whose handler lives in the main loop is to emit its EventBus signal directly rather than inject the key — mandatory for SHIFT-modified or F-key shortcuts (2026-07-14: verified the Shift+F4 onboarding-retrigger this way; `inject-key` both mis-maps F-key names AND silently drops the shift modifier, so it can't reproduce Shift+F4 at all). `inject-key`: key NAMES don't parse ("F5" → keycode 5, "Space" → error) — use NUMERIC keycodes (F1=4194332…F11=4194342, Space=32, Enter=4194309); the `shift` param is NOT honored on the synthesized event (Shift+F11 arrives shiftless). Injected keys reach `_input` handlers (F-keys work) but NOT the GUI focus dispatch (Enter won't activate a focused button). `inject-mouse-click` lands at (0,0) regardless of x/y. Bottom line: drive UI verification via argless runtime methods + screenshots; reserve injected keys for raw `_input` hotkeys only.

**New `class_name` scripts need a cache rebuild before ANY run (2026-07-14):** after creating scripts that declare `class_name X` (or referencing them via preload in an already-loaded script), a headless/MCP run fails with `Parse Error: Identifier "X" not declared in the current scope` / `Could not find type "X"` even though the code is correct — the global class cache (`.godot/global_script_class_cache.cfg`) is stale. Fix: run `--headless --import` once (prints `update_scripts_classes | X`), which registers the new globals; then the run parses clean. The `--import` pass ALSO imports new texture assets (e.g. renamed `.webp`) so runtime `load(path)` resolves. Do it after adding each batch of new `class_name` files, before editor-run.

**Pure-CLI headless smoke (no MCP, fastest for the `endgame_smoke` suite) (2026-07-14):** the console build is at `C:\Users\erdem\Desktop\Godot_v4.6.2-stable_win64_console.exe`. Loop cases from PowerShell capturing stdout via the pipe (`$out = & $exe --headless --path $proj --endgame-smoke=<case>`; then `$out | Select-String "SMOKE (PASS|FAIL)"`). Two gotchas: (1) a NEW `class_name` needs a scan first — `& $exe --headless --path $proj --editor --quit` registers it (prints `update_scripts_classes | X`), same effect as `--import`; without it every case fails `Identifier "X" not declared`. (2) `main.gd`'s smoke path historically `return`ed WITHOUT quitting (the "left ALIVE" note in `endgame_smoke.gd` is for MCP editor-run reading the live log), so a CLI run **hung** and file-redirected stdout never flushed. FIX now in `main.gd`: after `run_case`, `if _smoke_case_on_cmdline(): get_tree().quit()` — quits only when the arg is on the actual command line (CLI), leaves the MCP/`ProjectSettings.main_args` path alive. So CLI runs now self-quit + flush; the pipe capture works.
